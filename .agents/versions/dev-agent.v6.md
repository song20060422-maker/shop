## 〇、题面原文（只读，唯一验收口径）

### 前置约束（必须严格遵守，禁止擅自扩大需求范围）

1. 本项目是 Shop 小型商城交易系统，使用 Go 开发，数据库持久存储，禁止写死业务数据；所有 ID、数量、金额、时间全部从入参/数据库读取。
2. 严格遵循 AGENTS.md 项目约束文件，本次业务需求以提供的业务文档为准，需求没有明确的点需要记录假设清单，不能自行脑补业务。
3. 预置账号：买家、运营、仓库、客服；接口层做身份可信校验，**禁止客户端传 user_id 直接信任，防止越权访问他人订单**；不需要做登录注册，身份从服务端会话/请求上下文获取。
4. 货币单位：分；待付款订单超时时间 10 分钟，使用服务端时间，支持配置教学时钟用于演示；一个订单只能购买 1 种商品，购买数量只能 1~2 件。
5. 外部支付渠道全部使用 HTTP 模拟服务，模拟服务必须支持返回：支付成功、支付失败、超时、重复通知、退款成功、退款失败；可构造【迟到支付通知】场景。
6. 禁止实现范围：不要做购物车、部分退款、售后退货、真实物流、完整财务系统。

### 业务完整规则（逐条落实代码逻辑）

1. 【下单&库存占用】买家只能下单在售、库存充足商品；订单保存下单时刻商品快照（商品ID、价格），后续商品改价/上下架不修改历史订单；创建订单立刻占用可售库存；待付款订单：状态=待付款，有效期 10 分钟；买家手动取消 OR 服务端超时关闭，释放占用库存；重复执行关闭逻辑，库存只能释放 1 次，不能重复释放。
2. 【支付通知处理，重点异常】支付通知必须鉴权验签；校验订单匹配、金额匹配；同一渠道交易号不能归属多个订单；重复支付成功通知：只能记账 1 次，不能重复更新订单、不能重复增加收款；订单处于待付款有效期内收到合法支付通知 → 订单流转【待发货】；订单已经超时关闭/取消后，收到支付成功通知 → **不能恢复订单、不能恢复库存**，这条支付记录进入【异常支付待处理列表】交给客服处理；验签失败、订单不存在、金额不匹配全部落异常记录，可查询。
3. 【售前退款业务，并发竞争核心】仅【已付款、待发货】订单，买家才可以提交售前退款申请；提交退款申请期间，业务上锁暂停发货；客服可以审批同意/拒绝退款，必须填写处理原因；拒绝退款之后，订单恢复允许发货；⚠️并发竞争：退款审批同意和仓库发货请求同时到达，必须互斥，最终只能出现其中一种业务结果：要么退款成功，要么发货成功，不允许同时发生；客服同意退款之后，调用模拟支付渠道发起退款：渠道退款成功 → 更新订单状态退款完成，普通售前退款恢复商品可售库存；渠道退款失败 → 订单保留【退款处理失败】待客服重试；迟到支付带来的异常支付退款：**绝对不恢复商品库存**；已经发货的订单，拒绝售前退款申请。
4. 【仓库发货逻辑】仓库只能看到状态为待发货合法订单；一张订单只能登记发货 1 次；填写承运方、运单号；发货完成订单流转已发货；已发货订单不再受理退款。
5. 【运营能力】维护商品上下架、商品售价；不能直接修改订单状态、不能直接改写库存数字，库存只能由下单、取消、超时、退款业务流程变更；查询全部订单、收款/退款汇总统计；查看可售库存、库存流水记录；查看全部异常支付记录。
6. 【页面要求：最小可操作 HTML 页面】C 端买家页面：商品列表页、我的订单列表页、订单详情页（支持下单、取消待付款订单、申请退款）；B 端标签页：运营（商品维护、交易统计、全量订单查询）、仓库（待发货订单列表、发货登记表单）、客服（退款申请审核列表、异常支付待处理列表、异常处理记录）。

### 代码质量硬性要求

1. 核心业务必须加并发互斥保护，防止超卖、并发退款发货冲突；
2. Go 单元测试，业务包目标覆盖率 ≥85%；需要编写并发测试用例，复现争抢库存、退款发货同时请求场景；需要执行 race 竞争检测；
3. 使用 go vet、go fmt；所有错误必须捕获落库/打日志，不能吞 error；
4. 数据库设计：商品表、订单表、订单状态变更流水表、支付通知记录表、退款记录表、异常支付记录表、库存变更流水表；所有状态变更保留流水，异常记录不能直接删除修改；
5. 模拟支付服务独立代码，可模拟成功、失败、超时、重复通知、迟到通知场景。

### 交付产出

1. Go 后端完整代码，数据库初始化 SQL 脚本；2. 简单 HTML 前端页面；3. 模拟支付 HTTP 服务代码；4. 单元测试用例；5. 运行说明文档。

### 禁止行为

1. 禁止硬编码商品、订单、时间、金额数据；全部动态读写数据库；2. 禁止忽略任何异常分支，所有边界条件必须处理；3. 禁止越权漏洞：买家只能读写自己订单，仓库只能做发货，运营不能直接改订单状态；4. 不要自行新增需求；没有明确的业务点写进假设清单。

### 开发 Agent 证据要求

开发 agent 需要完成的内容：使用 AI Agent 完成业务开发，学生审核并修正其产出。需要保留的证据：开发会话、代码版本、审核和修正记录。Git 地址：`https://github.com/song20060422-maker/shop.git`。

## 三、业务规则实现矩阵（BR-01 ~ BR-12）

> "完成判据"必须是可观察事实（状态、数字、记录、错误码），不接受"已实现"。

| BR | 实现要点（GVA 落点） | 完成判据 |
|---|---|---|
| BR-01 购买资格与快照 | `service/order.go` 条件 UPDATE（`on_sale=1 AND available>=qty`，数量 1~2 由入参校验）；订单写商品/价格快照 | 下架或超量下单被拒且不创建订单；下单后调价/下架，旧单金额不变（AC-02） |
| BR-02 占用可见 | 同事务扣减 `products.available` + `inventory_ledger` 记占用负向流水 | 下单 2 件后可售立即 5→3；账实与流水一致（AC-01/03） |
| BR-03 10 分钟与释放 | `Cancel`/`CloseExpired` 条件更新；释放幂等；超时用服务端时间（`shop.pay-timeout` 可配教学时钟） | 取消/关闭各恢复一次；重复关闭可售不再变化（AC-03） |
| BR-04 通知校验 | `service/payment.go`：验签（HMAC-SHA256）→ 订单存在 → 金额一致 | 三项任一不满足即拒绝，不记款、不改单（AC-04） |
| BR-05 幂等与交易号唯一 | `payments.channel_txn_id` 唯一 + 同交易号跨订单拒绝；重复走幂等返回 | 同通知重发 2 次 `payments=1`；同交易号指向另一单被拒且该单状态不变（AC-04） |
| BR-06 拒绝可查 | `payment_notices` 记 `sign_ok/result/reason`；买家详情、客服/运营通知查询均可读 | 金额不符、未知订单、验签失败三类均能查到原因（AC-04/08） |
| BR-07 有效付款与迟到 | 仅 `pending_payment AND expire_at>now` 可推进 `paid`；已取消/关闭写 `abnormal_payments`，不恢复订单与库存 | 有效通知→待发货；关闭后通知→订单仍关闭、可售不变、异常列表 +1（AC-05） |
| BR-08 售前退款与互斥 | `refund.Apply` 锁定发货；`shipment.Ship` 仅允许 `paid`；审核拒绝回 `paid` 并写原因 | 申请期发货被拒且有原因；拒绝后可继续发货；退款审批×发货并发终态唯一（AC-06/07） |
| BR-09 渠道确认与恢复 | `callChannel` 成功才置 `refunded`；`restored` 闸门恢复一次；失败置 `refund_failed` 可重试 | 首次 fail 留待处理、库存不变；重试成功后可售 +件数（AC-06） |
| BR-10 迟到退款不补库存 | 异常支付退款走独立路径，不调用库存恢复 | 迟到退款成功后 `available` 与退款前完全一致（AC-05） |
| BR-11 发货唯一 | 条件更新 + `shipments` 唯一；已发货拒绝售前退款 | 二次发货被拒；已发货订单退款申请被拒（AC-07） |
| BR-12 核查与留痕 | `service/report.go` 收款/退款汇总、库存流水、异常列表；`operation_logs` 记录跃迁；异常只改自身处理状态 | 汇总=明细之和；异常处理后仍可查；无"改订单状态使异常消失"通路（AC-08/09） |

**实现纪律**（详见 00-index.md 第 2/3 节）：所有状态跃迁用"带前态条件的单条 UPDATE + 受影响行数校验"，禁止先读后写；禁止在 handler 里改状态；渠道调用走事务内闸门；仅唯一键冲突判"重复"，其它 DB 错误原样上抛；每次跃迁与业务同事务写审计留痕。

## 四、异常矩阵（E-01 ~ E-12）

| E | 场景 | 必须保证的行为 |
|---|---|---|
| E-01 | 并发下单争抢库存 | 原子扣减，不超卖，失败方明确"库存不足" |
| E-02 | 取消与超时竞争 | 幂等关闭，库存只释放一次 |
| E-03 | 通知重复投递 | 按交易号幂等，只记款一次 |
| E-04 | 验签失败/金额不符/未知订单 | 拒绝、留痕、结果可查 |
| E-05 | 成功通知迟到 | 不复活订单、不重占库存，转异常列表 |
| E-06 | 退款申请期间发货 | 拒绝并提示原因 |
| E-07 | 发货与退款审核并发 | 串行化/状态互斥，只一种合法终态 |
| E-08 | 渠道退款失败 | 保留 `refund_failed`，可重试至成功 |
| E-09 | 已发货申请退款 | 拒绝并说明原因 |
| E-10 | 越权访问/操作 | 明确拒绝，不泄露订单细节；角色只信 token，不信客户端传参 |
| E-11 | 重复发货/非法状态发货 | 拒绝第二次 |
| E-12 | 直接改单消除异常 | 无此通路；异常只能客服闭环 |

## 五、必须支持场景（S-1 ~ S-5）与演示开关

| 场景 | 操作序列 | 通过标准 |
|---|---|---|
| S-1 正常成交 | 运营上架 → 买家下单 2 件并付款 → 仓库发货 → 买家查运单 → 运营核查 | 全程状态正确；可售 5→3；收款 +全额；运单可查（AC-01） |
| S-2 缺货与弃单 | 20 并发下单 → 未付款单取消/超时关闭 → 另一买家再购 | 成功占用≤库存；释放后可再买；重复关闭不再释放（AC-03） |
| S-3 售前退款 | 付款 → 申请 → 仓库发货被拒 → 客服批准 → 渠道失败 → 重试成功 | 失败留记录；成功后已退款、可售恢复（AC-06） |
| S-4 迟到支付 | 关闭订单 → 迟到通知 → 客服异常列表处理退款 → 运营核对 | 订单仍关闭；库存不二次变化；收退款各一次（AC-05） |
| S-5 操作竞争 | 退款×发货并发、重复通知×退款通知、越权查看/处理 | 每类有明确结果；无脏数据（AC-07/08） |

**演示开关必须可控**：模拟渠道可发成功/失败/超时/重复/验签失败/金额不符/迟到通知；退款结果可切 `success|fail`；超时可缩短（教学时钟）但判断仍用服务端时间，演示值须注明。测试钩子受 `shop.demo-mode` 门禁，生产一律 403。

## 六、页面要求（P1 ~ P4）

题面要求最小可操作 HTML 页面（内置 5 标签页 `server/shop/web/`，不允许静态假数据），须对照原型说明补齐可见项：

| 页面 | 必须能看到 |
|---|---|
| 商品与订单（买家） | 价格、实时可售、数量 1~2、下单；订单状态、待付款剩余时间、付款/取消/申请退款、运单、退款结果 |
| 仓库待发货 | 可发货订单、承运方与运单号登记、被冻结订单及原因、发货尝试记录 |
| 客服退款与异常 | 待审退款（同意/拒绝必填原因）、失败待重试、异常支付列表与处理、通知处理结果 |
| 运营核查 | 可售/占用、已收款、已退款、未结异常；按订单看收款/退款/发货/异常与轨迹 |

## 七、工程落点（与 GVA 结合，不得越界）

| 层 | 路径 | 职责 | 禁止 |
|---|---|---|---|
| api | `server/shop/api/` | 绑定、身份、错误码映射 | 不写事务与状态判断 |
| service | `server/shop/service/` | 事务、状态机、库存守恒、渠道、审计 | 不在 handler 改状态 |
| model | `server/shop/model/` | 表、常量、DTO | 金额禁止浮点 |
| middleware | `server/shop/middleware/` | JWT、角色门禁 | 角色只信 token |
| initialize | `server/shop/initialize/` | 装配、迁移、种子 | 迁移幂等，失败即启动失败 |
| migrations | `server/shop/migrations/*.sql` | 建表与预置数据 | 已发布脚本不回改 |
| router | `server/shop/router/` | 公开/登录/角色分组 | 不自造冲突路径 |
| web | `server/shop/web/` | 内置演示页 | 不引入前端构建链 |
| utils | `server/shop/utils/` | 单号、HMAC、bcrypt | 密钥不入库、不打日志 |

框架侧只允许改 `server/initialize/router_biz.go`（装配）与 `server/config.yaml` 的 `shop` 段；**不改 GVA `system` 模块**，不另起 main/端口/连接池；数据必须落 MySQL（重启可查），禁止内存态冒充持久化。

## 九、测试与质量（同步 00-index.md 第 6 节）

- 自编代码整体语句覆盖率 ≥85%，核心包各 ≥85%：`shop/service`、`shop/api`、`shop/middleware`、`shop/config`、`shop/initialize`、`shop/router`。
- profile 必须单命令生成（禁止拼接）：`go test -p 1 ./shop/... "-coverprofile=coverage-single.out" "-coverpkg=./shop/..." -covermode=atomic -count=1`；共库测试一律 `-p 1` 串行。
- 基线（2026-11-13 拆分后）：并集 88.7%，service 85.5%，api 81.3%，adminapi 81.4%；覆盖率不足只能补真实业务路径，工具函数凑数视为低价值。
- 必测：正常、边界（数量 0/3、库存恰好用尽）、非法状态、重复操作、权限、并发（20 并发争抢库存、退款×发货、重复通知、并发重试）；并发路径必须 `-race`；router 测试不得只断言状态码，库存与金额要有对账断言。
- 集成测试不得替代单元测试；缺陷走"发现 → 修正 → 复测"，写入 `docs/review_records.md`。

## 十一、红线

- 不编造接口、执行结果、测试报告、覆盖率、部署记录；未跑过的命令不写"已验证"。
- 不删失败测试、不弱化断言、不跳过关键路径、不排除生产代码。
- 不使用不存在或与清单不符的任务编号。
- 不直推 `main`、不 force-push、不跳过 PR 检查。
- 密钥、令牌、个人信息不得进入代码、日志、截图、会话导出。
- 不扩大范围：购物车、多商户、真实物流、部分退款、签收退货、完整财务、真实第三方支付。
- 不改 `AGENTS.md` 约束条款（只提请学生修订）；未确认假设不落地。
- 不把模拟渠道与框架能力包装成自研成果。

## 十二、交接给学生的固定格式

1. 工作项：T 编号 + 本次覆盖的 BR/AC 编号。
2. 变更：文件、接口、表；标明框架新增/修改边界。
3. 自测：命令 + 输出摘要 + 退出码 + 覆盖率 + race。
4. 判据：按 AC 逐条对照（通过/未通过，未通过写原因）。
5. 不变量：INV-1~INV-4 是否仍成立（给数字：INV-1 库存守恒；INV-2 同一渠道交易号至多归属一单；INV-3 每单至多一次成功发货；INV-4 每单至多一次成功退款）。
6. 风险与待确认：假设编号、需学生裁决项。
7. 下一步：下一工作项与依赖。

学生审核发现问题时，按"问题 → 修正要求 → 复测证据"回填 `docs/review_records.md`，修完再交下一项。
