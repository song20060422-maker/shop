# 02 · 工作流与 Git（提交规范与门禁）

> 每次提交前必读。提交格式细则依据仓库根 `commit-convention.md`（教师来源副本，原文不改写）。

## 工作项流程

1. 读本文件 + 需求基线材料，列出本次 BR 与 AC。
2. 提交工作项清单：`T 编号 | BR | 影响文件 | 完成判据（引用 AC）| 依赖`，确认后动工。
3. 每项：实现 → 按 AC 自测 → 留证据 → 下一项；禁止一次写完再补过程。

## 分支

分支 `dev/<题号>`（当前 `dev/01-shop`）；禁止直推 `main`、force-push、跳过钩子。

## 提交规范

格式 `[类型] [版本号] [编号] 中文描述`：

- 类型 `feat/fix/hotfix/opt/docs/test`，一次 commit 只一种类型，混合变更拆分；不得把功能变更伪装成 docs/test/opt。
- 版本号 `v{主版本}.{次版本}.{修订号}`；描述使用简洁中文。
- 编号：feat/fix **必填**真实飞书工作项 ID（`#数字`，需求或缺陷单）；hotfix 编号可事后补（保留补录记录）；opt/docs/test 可选。工程内 T 编号（`docs/dev_log.md`）作为工作项索引，须与提交编号对应，不得编造。
- 编号核验：feat/fix 提交前执行 `meegle workitem get --work-item-id {数字} --project-key r17te9` 并保留真实输出；编号不存在或查询失败时提醒开发者确认，未完成核验不得视为合规提交，禁止伪造编号或谎称查询成功（meegle 本机不可用时如实注明并记入假设清单）。

## 提交前门禁（缺一不可）

- `gofmt -l shop` 空输出、`go vet ./shop/...`、`go build ./...`、`go test ./shop/... -count=1`；并发路径追加 `go test -race ./shop/service/`。

## 证据随交

变更文件清单（挂 BR）、自测命令+真实输出+退出码、覆盖率单命令 profile、缺陷记录写入 `docs/review_records.md`。未执行的命令不得写"已验证"。

## 交接固定七段

工作项（T + BR/AC + 提交哈希）→ 变更（文件/接口/表、框架边界）→ 自测（命令+输出+退出码+覆盖率）→ 判据（按 AC 对照，未过写原因）→ 不变量数字 → 风险与待确认（假设编号）→ 下一步。
